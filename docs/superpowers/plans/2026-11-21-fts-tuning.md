# FTS5 tuning experiment plan

**Goal:** Measure untuned FTS5 indexing, search and retrieval on pinned corpora before comparing the three independent alternatives in #255. Deliver reproducible measurements, not a production migration or a ranking change.

## Pre-tuning baseline

- Start with the merged C/Java chunker from #272 on `origin/main`. Record the release Git revision, SHA-256 of both locked release binaries, Rust toolchain, bundled SQLite, database schema and derived-data versions. Treat the C forward-typedef change in #283 as a distinct source revision: if it lands during the work, rebuild and rerun on the new base before comparing variants. Do not reuse exploratory databases.
- Use a new temporary run directory with private data and cache paths. Copy only pinned source inputs into that cache as needed; never write to existing checkouts or indexes. Verify local checkouts against explicit commits with no tracked changes or indexable untracked files; check again after measurement. Keep the exact manifests, hashes and source pins. Measure FHIR first, Linux v6.18 as the scale corpus, Kubernetes as the structured non-identity holdout, and Keycloak and identity separately. Verify Linux's actual chunk count before applying the million-chunk target.
- Before running search, freeze source-verified labels for exact and ambiguous symbols, rare and broad terms, plain-language code questions, path filters and no-result controls. Preserve the existing retrieval and history manifests and labels unchanged; score them with `codecite-bench`. Use the same labels for every arm. Report the first relevant rank, Recall@1, Recall@10 and MRR@10 for labelled positive cases, empty-result violations for misses, definition ambiguity separately, and citation read-back failures separately. Store citations and outcomes, not result snippets.
- Run two fresh/unchanged index pairs per scale/domain corpus, sequentially and without competing benchmark jobs. Use GNU `time` for wall time and peak RSS; record process exit and per-run summary counts, final database and FTS posting bytes, segment count, documents, chunks, symbols and skip counts. Compare unchanged runs with their corresponding fresh runs; a changed corpus invalidates the no-op measurement.
- Time fresh CLI subprocesses and requests through a single persistent MCP process separately. MCP reopens the database per tool call, so this measures warm process and OS page cache, not connection reuse. Use one untimed sweep followed by deterministic repeated sweeps at depth 10, with no OS cache eviction. Measure p50/p95 and sample count by corpus, query class and mode; report Linux against the 100 ms p95 target separately. Keep individual samples and check both modes agree on ranked citations.

## Isolated alternatives

- After measuring the quality baseline, test `detail=column` in an experiment build on fresh data; compare index time, posting bytes, query latency and ranking on identical inputs. Run the frozen retrieval and history labels and the non-identity holdout for any ranking-changing comparison.
- Measure per-document path postings against repeated chunk paths on FHIR and identity before investing in a joined ranking prototype. If warranted, compare the prototype to the same untuned baseline, keeping it separate from `detail=column` and `optimize`.
- Measure FTS5 `optimize` by itself on isolated databases: index/maintenance cost, peak WAL, final bytes and segments, and paired search/quality. Preserve identical logical contents on the pre/post comparison; a threshold recommendation requires measured rewrite fractions, not extrapolation from a single fresh build.
- Keep each alternative and its results reproducible under `experiments/fts-tuning/`. No candidate pre-cut or production tuning in this change. Report tradeoffs per corpus without pooling away regressions. Run workspace fmt, locked clippy and locked tests before committing. Do not publish, push, or dispatch model evaluations.
