# Rank by k Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make a search's cost depend on its result limit, not on how many chunks match (#251), without changing any result.

**Architecture:** Store what ranking reads per candidate at write time: `symbol.name_key` (indexed) and `document.role` / `document.role_weight`. Rank in two phases: phase 1 orders candidate rowids by the same score expression and tie-breaks, `LIMIT k`, reading no text; phase 2 reads text, citations and snippets for those k chunks only. Migration 0010 adds the columns and Rust backfills them in the migration's transaction.

**Tech Stack:** Rust, rusqlite with bundled SQLite, FTS5.

**Spec:** issue #251; `docs/design.md` (Indexing and retrieval: Ranking, Write).

## Global Constraints

- The ordered citations of every retrieval-benchmark query are identical before and after.
- Score is computed as `-bm25(chunk_fts, 10, 5, 1) * role_weight * boost`, in that order, so it is bit-identical to the old `codecite_role_weight(...)` product.
- No `ORDER BY rank` pre-cut (the issue's fourth bullet): it changes results.
- The migration takes the next free number on `main` (0010); later landers renumber.

## Review Focus

- An existing version 9 corpus opened by the new build: every symbol gets a `name_key` and every document a role and weight, so it ranks exactly as a fresh index does.
- A corpus opened read-only at version 9 is still refused (unchanged behaviour); `codecite index` upgrades it.
- A symbol whose name holds non-ASCII letters: `name_key` folds case as Rust's `to_lowercase` does, not SQLite's ASCII `lower()`, so the key is computed in Rust.
- `--only spec` / `--only code` filter on the stored role and keep exactly the old sets.
- Equal scores keep the old tie order (source name, path, start line, end line) across both phases.
